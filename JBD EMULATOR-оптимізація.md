### Чому XiaoxiangBMS працює, а Overkill Solar пише «no connected BMS»?  
  
Це класична апаратна особливість емуляторів JBD на ESP32. Проблема полягає в **розмірі BLE MTU та відсутності розбиття пакетів на чанки (Chunking)**:  
  
1. **Довжина пакета JBD перевищує стандартний ліміт BLE (20 байт)**:  
   * Відповідь на запит **`0x03` (Basic Info)** має розмір **34 байти** (заголовок + 27 байт даних + 2 байти CRC + `0x77`).  
   * Відповідь на запит **`0x04` (Cell Voltages для 8S)** має розмір **23 байти**.  
2. **Різниця між додатками**:  
   * **XiaoxiangBMS** (від *smagicld*) — сучасний додаток, який при підключенні на iOS запитує розширення MTU (MTU Exchange до 512 байт). Тому він приймає всі 34 байти одним шматком без проблем.  
   * **Overkill Solar** (та оригінальний додаток Jiabaida) писалися під старі фабричні чіпи JBD (TI CC2541 / BLE 4.0). Вони **не розширюють MTU**, а очікують, що Bluetooth-модуль сам ділить відповіді на шматки по **20 байт** (максимальний корисний payload при стандартному MTU 23).  
3. **Що відбувається на ESP32**:  
   * Якщо прошивка емулятора робить `pNotifyCharacteristic->setValue(data, 34); pNotifyCharacteristic->notify();`, при нерозширеному MTU стек BLE мікроконтролера **обрізає (truncate) пакет до перших 20 байт**, а решту 14 байт просто відкидає!  
   * У результаті Overkill Solar отримує «обрубок» пакета без кінцевого байта `0x77` та без контрольної суми CRC16.  
   * Додаток вважає пакет пошкодженим, відкидає його і після 3 секунд тайм-ауту показує напис: **`no connected BMS`**.

### Як це виправити  
  
#### 1. Виправлення в коді емулятора (проєкт `JBD-bms-emulator`)  
  
У коді відправки відповідей через `pNotifyCharacteristic` (характеристика `0xFF01`) надсилання довгих пакетів має відбуватися шматками по **максимум 20 байт** із затримкою 10–15 мс між ними:  
  
```cpp  
// Функція відправки відповідей з розбиттям на 20-байтні чанки  
void sendJbdResponse(const uint8_t* data, size_t length) {  
    if (!pNotifyCharacteristic || !deviceConnected) return;  
  
    size_t offset = 0;  
    while (offset < length) {  
        // Стандартний розмір чанка BLE 4.0 — не більше 20 байт  
        size_t chunkSize = (length - offset > 20) ? 20 : (length - offset);  
          
        pNotifyCharacteristic->setValue((uint8_t*)&data[offset], chunkSize);  
        pNotifyCharacteristic->notify();  
          
        offset += chunkSize;  
          
        // Обов'язкова мікропауза для стеку iOS CoreBluetooth  
        if (offset < length) {  
            delay(15);   
        }  
    }  
}  
```  
  
#### 2. Перевірка прапорців характеристики запису `0xFF02`  
Переконайтеся, що характеристика прийому команд підтримує обидва типи запису (з відповіддю і без відповіді), оскільки Overkill Solar використовує `WRITE_NR`:  
```cpp  
pWriteCharacteristic = pService->createCharacteristic(  
    NimBLEUUID((uint16_t)0xFF02),  
    NIMBLE_PROPERTY::WRITE | NIMBLE_PROPERTY::WRITE_NR  
);  
```  
  
#### 3. Перевірка на боці iPhone (перед тестом)  
* Обов'язково **вивантажте (Force Close / свайп угору) додаток XiaoxiangBMS**, щоб він не утримував BLE-сесію у фоні, оскільки ESP32 може працювати тільки з одним клієнтом.  
* Перезавантажте ESP32-C6 і підключіться знову через Overkill Solar.  
  
Як тільки відповіді на регістри `0x03` та `0x04` надходитимуть чанками по 20 байт, Overkill Solar успішно зведе пакети до купи, розрахує CRC, і на головному екрані миттєво з'являться всі напруги 8 осередків, струм, SOC 96% та температура!
