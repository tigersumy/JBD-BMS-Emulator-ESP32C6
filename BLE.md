При роботі з **JBD BMS через Bluetooth Low Energy (BLE)**, взаємодія побудована на специфічній структурі сервісів і логіці команд, де згадка 0xFF та автентифікація мають ключові особливості. \[1, 2\]

## **1\. BLE Сервіси та Характеристики (Протокол FF00)**

Плата JBD BMS (також відома під брендом додатка [Xiaoxiang](https://github.com/Voidmonk16/bms-guardian-android) або як [Overkill Solar](https://github.com/FurTrader/OverkillSolarBMS/blob/master/Comm_Protocol_Documentation/BLE%20_bluetooth_protocol.md)) використовує пропрієтарний профіль GATT, де сервіси ідентифікуються за допомогою UUID з діапазону **FF00**: \[3, 4\]

> *   
> * **Service UUID:** 0000ff00-0000-1000-8000-00805f9b34fb  
> * **Notification Characteristic (Rx):** 0000ff01-... (сюди BMS надсилає відповіді)  
> * **Write Characteristic (Tx):** 0000ff02-... (сюди ви записуєте команди) \[1, 3\]  
> * 

## **2\. Логіка автентифікації та пакетів "0xFF"**

У деяких специфічних або новіших прошивках JBD BMS (а також кастомних модифікаціях на кшталт Fogstar Drift) перед відправкою стандартних UART-команд (які інкапсулюються в BLE-пакети) через характеристику 0xFF02 вимагається процедура рукостискання (Handshake). \[1, 3, 5\]

> *   
> * **Пакет автентифікації:** Для авторизації сесії клієнт має надіслати спеціальний сервісний фрейм. Зазвичай він починається або містить маркер 0xFF у полі типу команди (на противагу стандартному 0x03 для читання чи 0x5A для запису).  
> * **Введення пароля:** Якщо в налаштуваннях BMS встановлено PIN-код (за замовчуванням 000000 чи 123456), цей пароль передається у вигляді байтового масиву всередині авторизаційного пакета.  
> * 

## **3\. Проблема безпеки "Косметичної автентифікації"**

Дослідження кібербезпеки апаратного забезпечення розумних BMS показали важливий нюанс: у більшості стандартних плат **JBD (наприклад, моделі DP04S007)** захист паролем реалізований виключно **на рівні інтерфейсу мобільного додатка**, а не на рівні самої прошивки мікроконтролера BMS. \[6\]

Якщо ви надсилаєте прямі BLE-команди в обхід офіційного додатка (наприклад, через скрипти на Python з бібліотекою bleak або модуль [ESPHome](https://github.com/syssi/esphome-jbd-bms)), плата часто приймає команди читання та навіть керування силовими MOSFET-ключами **взагалі без проходження автентифікації**. \[6, 7\]

## **Структура фрейму для передачі через BLE**

Всі команди, які пакуються для відправки в характеристику 0xFF02, дублюють стандартний UART-протокол Jiabaida: \[1, 3\]

| Байт | Значення | Опис |
| :---- | :---- | :---- |
| 0xDD | Старт фрейму | Маркер початку пакета |
| 0xXX | Команда / Реєстр | Наприклад, 0x03 (загальні дані) чи сервісний 0xFF |
| 0xXX | Довжина даних | Кількість байтів, що передаються |
| 0xXX .. | Дані | Пароль або параметри (якщо є) |
| 0xXX 0xXX | CRC Checksum | Двобайтова контрольна сума (16-bit) |
| 0x77 | Стоп фрейму | Маркер кінця пакета |

Щоб допомогти вам із конкретною реалізацією, уточніть:

> * Ви пишете **власний код** (наприклад, для ESP32/Arduino) чи налаштовуєте готову інтеграцію (на кшталт Home Assistant)?  
> * BMS **відхиляє підключення** чи видає помилку типу 0x80 (Access Denied) при спробі зчитати дані?
